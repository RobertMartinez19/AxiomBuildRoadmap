02Phase 2

ToF Sensor Demo Waiting on boards

Your first rep with real ST hardware. Goal: not just a working demo, but a short characterization of the part's real-world performance, which is the thing an FAE actually gets judged on. No video exists for this; follow the steps.

0/5

Install STM32CubeIDE and set up the board

Kit: P-NUCLEO-53L8A1 (Nucleo board + VL53L8A1 ToF expansion) plus a second sensor variant on the SATEL-VL53L8 satellite board. Both are self-contained, so no external Arduino is needed.

  1. Download and install STM32CubeIDE (free, from st.com) and STM32CubeMX. You can do this one now, before the boards arrive.
  2. Connect the Nucleo board to your Mac over USB. It has a built-in ST-LINK programmer, so no separate programmer hardware is needed.
  3. In STM32CubeIDE, check for an official example project for the VL53L8A1 (ST publishes X-CUBE expansion software packages with ready-made ranging examples). Start from that instead of writing the driver code from scratch.
  4. Build and flash the example, then open a serial terminal to confirm you're getting live distance readings.

Get the example ranging code running cleanly

  1. Use STM32CubeMX to confirm the pin/peripheral configuration matches the expansion board. It auto-generates this for known X-NUCLEO boards, so select the correct expansion in the pinout tool rather than configuring pins by hand.
  2. Run the official example unmodified first. Don't customize until you've confirmed baseline readings work.
  3. Watch the distance output as you move your hand toward and away from the sensor to confirm it's live and responsive.
  4. Once the first sensor works, repeat setup for the SATEL-VL53L8 satellite board so you have two sensors to compare in the characterization step.

Build the triggered demo

Wire an LED or buzzer from the Smraza kit so it triggers when an object enters a set distance threshold.

  1. Pick a threshold (e.g. under 300mm) and add an if (distance < threshold) check around your existing read loop.
  2. Drive an LED or buzzer high when the condition is true, low otherwise.
  3. Confirm the trigger feels responsive. If it lags, shorten your read/loop delay.

03Phase 3 · Capstone

Code Axiom Full build

Table-mounted claw, speaking through a gutted 3rd-gen Echo, woken by "Axiom," powered by the Claude API. Layered wake design: the ToF sensor detects when you approach and puts the system into a low-power "alert" state, but only the spoken word "Axiom" actually triggers a response. The N6 board is the ears, the ToF sensor is the sense of presence, the Uno + servos are the hands, your MacBook is the brain, and the Echo speaker is the mouth.

0/10

Stage 1: Salvage the Echo

Get the speaker driver and enclosure out cleanly. Don't rely on the Echo's own mic array or its internal electronics for anything else.

  1. Unplug it, then search "3rd gen Echo teardown" for a disassembly guide (iFixit has one). It uses hidden screws under the rubber base and a bit of prying, not obvious from the outside.
  2. Identify the round speaker driver and its two wires (positive/negative, often red and black or marked with a + on one terminal).
  3. Cut the speaker's wires a few inches from the driver, leaving enough length to work with. Set aside the rest of the internal boards; you won't use the mic array or the Echo's own processor.
  4. Keep the plastic housing if you want the final build to look like a proper enclosure rather than exposed electronics.

Stage 2: Wire the speaker through an amplifier

The salvaged speaker needs amplified audio, not a bare line-level signal. This is what the PAM8403 amp board is for.

  1. Wire the PAM8403's speaker output terminals to the two wires you cut from the Echo's driver.
  2. Wire the PAM8403's audio input to your MacBook's headphone/audio-out jack (a cheap 3.5mm cable cut in half works, or an aux cable with bare wire ends).
  3. Power the PAM8403 from a 5V source. A spare USB cable works; most of these boards accept 5V over USB power pins.
  4. Test it early: play any audio from your MacBook and confirm sound comes out of the salvaged speaker before building anything else on top of this.

Stage 3: Wire the ToF presence gate

This runs before the wake word and gates it. With no one nearby, the system idles. When someone approaches, it moves to "alert" and starts actively listening for "Axiom."

  1. Mount a ToF sensor facing outward from the table, roughly where someone would stand to talk to it.
  2. Wire it to the N6 board over I2C (same connection pattern as Phase 2, different host board).
  3. Write simple logic on the N6 board: while no object is within a set range (e.g. under 1.5m), stay idle/low-power. The moment something enters range, switch to an "alert" state. This is also a good moment for a visual cue (an LED) so the demo video shows the system visibly waking up.
  4. Confirm this triggers reliably as you walk toward the table and drops back to idle when you step away, before moving on to wake-word detection.

Stage 4: Get the N6 board listening for "Axiom"

This is the hardest software piece in the whole project, so budget real time for it. It only needs to run while the presence gate from Stage 3 is in "alert" mode, not constantly.

  1. Connect a microphone to the NUCLEO-N657X0-Q. Check its datasheet for the mic input; it may need a digital MEMS mic on a breakout, or accept one over an onboard connector.
  2. In STM32CubeIDE, look for ST's audio/keyword-spotting example project in the X-CUBE-AI or Model Zoo packages. Start from a working example rather than training a model from scratch.
  3. If ST's example uses a different wake word, keep their example word working first, confirm the whole pipeline, and swap in your own trained "Axiom" model second. Don't debug two unknowns (the hardware pipeline and a custom word) at the same time.
  4. Gate this loop behind Stage 3's "alert" state, so wake-word detection only runs when the ToF sensor says someone's there. This is the power/false-trigger benefit of the layered design.
  5. Once "Axiom" reliably triggers, add a simple action: light a second LED or print over serial, so you can confirm detection before wiring it to anything else.

Stage 5: Bridge the wake word to your MacBook

  1. Connect the N6 board to your MacBook over USB (it will show up as a serial device).
  2. On the N6 side, send a simple message (like the text "WAKE") over serial the moment it detects "Axiom."
  3. On the MacBook side, add a small piece of code to your existing Axiom project that watches that serial port and starts your normal listen-and-respond flow the moment "WAKE" arrives.
  4. Test end to end: say "Axiom," confirm your MacBook's existing code kicks in exactly like it does today when you trigger it manually.

Stage 6: Build the claw and wire the "hands"

This is where your Phase 1 servo work and the ToF sensor from Phase 2 both come back directly.

  1. Assemble or 3D-print a small claw/gripper mechanism sized for 1–2 SG90 servos (many free claw designs exist for exactly this servo).
  2. Wire the servos to the Uno the same way you did in Phase 1.
  3. Mount one ToF sensor near the claw's grip point, wired to the Uno over I2C.
  4. Write a simple Uno sketch: wait for a serial command, check the ToF reading, only close the servo if something is within a set distance, then report back "done" or "nothing there" over serial.
  5. Connect the Uno to your MacBook over its own USB cable (a second serial connection, separate from the N6 board's).

Stage 7: Tie it all together

  1. In your MacBook's Axiom code, add logic so that when Claude's response implies a physical action ("grab it," "pick that up"), it sends the matching command over the Uno's serial connection.
  2. Route Axiom's spoken response through the PAM8403 amp/Echo speaker instead of your MacBook's built-in speakers.
  3. Run a full loop: say "Axiom," ask it to grab something, confirm the claw only closes when the ToF sensor sees an object, and confirm the response plays through the salvaged speaker.

Stage 8: Mount everything on the table base

Make it look like one finished object, not a pile of wired boards.

Stage 9: Document the build and the thinking behind it

This is the actual portfolio centerpiece. Write up the decisions (why five separate parts instead of one board doing everything, what broke, what you'd do differently), not just a parts list.

Stage 10: Film the final demo

Same shot-list structure as the ToF video: intro, live demo, what's happening under the hood, and a wrap-up on what you'd tell someone evaluating this approach.
